# PR羅針盤 — 決定の記録

配信が止まっている企業に対し、対話で「次の1本」を確定させる機能
（`feature/pr-compass` と `/pr-compass`）について、実装から読み取れない判断だけを残す。

同じ機能が 2 つ独立に実装された時期があり、実データで検証済みだった
`feature/pr-compass` を正として一本化した。この文書はその過程で確定した事柄の記録。

---

## 1. 仕様の数値のうち、実データが否定したもの

当初のシステムプロンプトの出力例には、実測と矛盾する数値が含まれていた。
プロトタイプ（`voice-agent/`）は 2026-08-13 に prtimes RDS を実測しており、そちらを正とする。

| 仕様の例                                   | 実測                                                        | 採否         |
| ------------------------------------------ | ----------------------------------------------------------- | ------------ |
| 1本目のPV中央値 820 → 6本目 1,340（1.6倍） | **PV中央値は本数を重ねても伸びない**（情報通信で 13 → 12）  | **使わない** |
| メディア転載率 1本目5% → 6本目28%          | **転載はほぼ全リリースで起きるため転載率では差がつかない**  | **使わない** |
| —                                          | PVの裾が極端に長い（中央値25 / 上位10% 128 / 上位1% 1,487） | 採用         |
| —                                          | 当たり率 1本17% → 3本29% → 6〜10本47% → 21本以上87%         | **中心指標** |

したがって中心指標は
**「配信本数別に、業種内PV上位10%に届いた企業の割合」**（当たり率カーブ）。

言い方は「**1本ごとがくじで、本数を重ねるほど当たりを引く確率が上がる**」になる。
「1本あたりの反応が良くなる」ではない。ここを取り違えると全部の文章が嘘になる。

期間カーブは**当たり率カーブと対で**使う。本数では 17%→87% に上がるのに、
時間では 3 年経っても 13%→23% にしかならない。この対比があって初めて
「時間ではなく本数」という主張が成立する。片方だけでは意味がない。

### 統計上の限界

当たり率カーブは相関であって因果ではない。
「21本出した企業の87%が当たり」は「当たった企業が出し続けた」でも説明できる（生存者バイアス）。

文章は「差があります」と書き、「上がります」と書かない。
仕様の禁止事項「数値の裏付けがない断定」「事例がないのに『できます』と言うこと」と同じ制約。

## 2. LLM に会話を駆動させない

```
数値・判定・機能選定 … SQL とドメインルール（決定的）
文章                 … LLM（下書きを言い換えるだけ）
```

LLM に渡すのは**日本語ラベルの辞書**と**テンプレの下書き**だけ。
生の指標名（`eval_point` 等）を渡すと意味を誤読するため、指標の定義そのものをキーにする。

`classifier` は自由入力を分岐に落とすだけ、`narrator` は下書きを言い換えるだけで、
どちらも**数値を作る経路を持たない**。提案する機能もカタログの定数からしか選べないので、
実在しない機能の提案が構造的に起きない。

キーが無くてもテンプレのまま会話が成立する（`OPENAI_API_KEY` は optional）。

### 段はターン数で進めない

以前はアシスタントの発言数がそのまま進行度だった（0本目=診断、1本目=理由、2本目=提案）。
相手が何を書いたかに関係なく 3 通目で提案に到達するため、聞けていなくても提案が出る。

現行は、段ごとに「聞いたことが取れたか」で進める。

| 段          | 取れたら                   | 取れなければ                      |
| ----------- | -------------------------- | --------------------------------- |
| `diagnosis` | 診断を出して `reason` へ   | —（ここだけ相手の答えを待たない） |
| `reason`    | 処方を出して `interest` へ | 問いを狭めて聞き直す              |
| `interest`  | 提案を出して `react` へ    | 言い方を変えて聞き直す            |
| `react`     | 反応に応じて分岐           | どこが引っかかったかを聞き直す    |

判定は分類器に寄せた。`Classifier` は `null`（＝取れなかった）を返せる。
`unclear` を選べるようにしてあるのは、質問・相槌・雑談まで既定の分岐に落ちるのを止めるため。
既定値へ倒すと、聞けていないのに会話だけが先へ進む。

留まり続けないよう、同じ段で `MAX_STALLS` 回聞き直したら既定に倒して先へ進む。
`OPENAI_API_KEY` が無いと分類は常に空になるため、この逃げ道が無いと会話が止まる。

「ピンとこない」の内訳（`Objection`）も分類器に通し、断られるたびに引き出しを変える。
回数で切り替えると同じ提案の言い換えになるため、開けた引き出しは `tried` に控えて二度出さない。

## 3. `stats` 接続は PR TIMES DB

`STATS_DATABASE_URL` は PR TIMES のデータベースを指す。
役割（外部・参照専用・マイグレーションを流さない）がそのまま一致するため、接続は増やさない。

- 統計 DB を読むのは `feature/pr-compass` **だけ**。SQL は他の場所に置かない
- ローカル代役は `docker/stats-db/init.sql`。実 RDS との照合は未了なので、
  繋いだら `pnpm db:stats:pull` で引き直して差分を確認すること
- `release_statistic` / `release_keyword` の JOIN は必ず `(company_id, release_id)` の
  複合キーで行う。`release_id` 単独では一意にならず、他社のリリースを巻き込む
- 骨組みのサンプルだった `agent_daily_stats` と `feature/stats` は削除済み

### 生の SQL は時刻を文字列で返す

CTE を多用する集計はクエリビルダで書けず生の SQL になるが、その戻り値は
ドライバの型パーサを通らず `'2025-11-13 16:50:16'` のような文字列で来ることがある。

`Date` と宣言した場所に文字列を通すと、`Intl.DateTimeFormat#format` が引数を
`ToNumber` するため `NaN` になり `RangeError` で落ちる。`getTime()` も落ちる。
どちらも「値が無いとき」ではなく「**値があるとき必ず**」落ちる。
境界で必ず `Date` に正規化すること。

### 集計は重い

業種単位の集計は業種の全リリースを走査する（種別ごとの傾向で約9秒、打ち手の差分で約30秒）。
`stats` 接続には `statement_timeout` 180 秒を設定してある。上限が無いと、
詰まった 1 本が参照専用プールの接続を握ったまま他のリクエストごと巻き込む。

## 4. 認証

合言葉 1 つの簡易ログイン（`feature/auth`）。詳細は `README.md` の「簡易ログイン」。

ログイン後に企業を 1 社選び、その企業として使う。企業一覧
（`prCompassFeature.findStoppedCompanies`）は統計 DB を読むので `pr-compass` に置いている。
認証が利用者と企業を結びつけるようになったら、この一覧は要らなくなる。

## 6. 実データで未確認のこと

プロトタイプが積み残し、現在も確認できていないもの。

- `capital` の分布（照合軸を `業種 × 規模 × PR内容` に広げるときの前提）
- 業種だけで絞ったときの社数（件数が枯れたときに軸を緩める段の設計に要る）
- `ipo_type` / `lead_paragraph` / `release_business_category` / `release_location` の実在と充足率
- `release.created_at` が `timestamptz` か `timestamp`（JST 格納）か。
  後者だと日付が 1 日ずれる

## 7. 経緯（Notion との差分）

Notion の「目的の抽出」ページには、これと正反対の対話設計が書かれている。

| 論点         | Notion「目的の抽出」                       | 現行                                                             |
| ------------ | ------------------------------------------ | ---------------------------------------------------------------- |
| 質問形式     | 自由回答のオープンクエスチョン             | 自由入力 + サジェスト                                            |
| ラダリング   | 「なぜ」「それが実現したら」を積極的に使う | **使わない**（全企業が同じ答えを返し、事例照合の入力にならない） |
| 目的の階層   | 対話して3階層を作る                        | 裏で推定するだけ                                                 |
| ターン数     | 完成サンプルで17問                         | 最短4往復。答えが取れなければ聞き直すので、その分は伸びる        |
| 言い換え確認 | 「〜という理解で合っていますか？」が型     | 情報量ゼロとして使わない                                         |

Notion 側が古い検討過程なのか、別機能として残すのかは未決。
2日目の振り返りに「抽象的な議論を続けてきたこともあり、具体的に技術的な処理方法を
検討する中で認識の違いに気づくことがありました」とあり、転換自体は記録されている。
